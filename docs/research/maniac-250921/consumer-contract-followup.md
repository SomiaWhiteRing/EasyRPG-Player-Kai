# Maniac 消费链复核：图片回归根因与系统性补完规模

分析日期：2026-10-14；有限修复日期：2026-10-15。§1–6 保留源码基点 `5c64d306c` 的静态调查快照；分析阶段没有修改源码或运行目标。随后按用户要求完成的有限修复与检查见 §7。两个阶段均没有人工 UI、原版运行对照、逐条执行全部指令或新增永久测试代码。

## 1. 结论及有限提交的状态

先前有限修复已经在 `5c64d306c fix: complete Maniac picture and event decoding` 提交；分析开始时跟踪文件干净，无需再制造一份相同提交。其前一份合同修订为 `0d7d3301b`。

**本轮推翻这两份提交依据中的一项核心判断：MovePicture 的 relative 不是只移动位置并保留其他目标。原版会将位置、宽高缩放和透明度分别加到既有目标上；RGB/饱和度由独立的 keep-RGBs 位控制，不作相对加法。** 先前把反编译控制流中的绝对分支与相对分支误读为“写入与跳过”，有限修复因此把旧的错误覆盖改成了错误保留。

此外，MovePicture 对普通非负时长会产生至少一帧的过渡；当前实现对 0 产生 0 帧，却沿用原版“不在 remaining=0 时更新普通属性”的更新器。生产者与消费者分开看都很接近原版，连接起来却使无时长移动完全不生效。

这两个共享缺陷能从游戏实际编译指令和当前代码中解释：尾迹不随残影年龄缩小/淡出、得分结算文字及背景不退场、右侧文字保持白色和放大、底部滚动说明留在屏幕外，以及一些从零缩放或完全透明状态入场的文字不可见。它们不是需要为每种文字或每颗弹球新增的游戏特例。

## 3. 原版 MovePicture 的真实合同

### 3.1 relative 按字段工作，RGB 的开关独立

原版 `0x14003c6f0`：

|字段|relative=0|relative=1|其他控制|
|---|---|---|---|
|X/Y|写入求值后的目标坐标|求值结果加到既有目标坐标|原点转换、随地图滚动的坐标分支需独立保留|
|宽度/高度缩放|写入求值后的目标缩放|求值结果加到各自既有目标缩放|高度未独立指定时沿用宽度参数的求值结果|
|透明度|写入求值后的目标透明度|求值结果加到既有目标透明度|透明度 100 表示完全透明|
|RGB/饱和度|写入求值后的色调目标|同样写入求值后的色调目标|`options & 0x04` 才保留既有色调|
|文字 style word|按掩码更新|按掩码更新|blend/flip 保留位、字体大小及图片类型是独立规则|
|特效|按自身模式更新|按自身模式更新|`options & 0x08` 的保留逻辑独立|

所以 `.relative .scale(0)` 确实不改缩放，但原因是“加 0”；`.relative .scale(-20)` 则必须把 120 改到 100。不能从前一个例子推导出“relative 保留缩放”。`.relative .rgbs(100,100,100,100)` 在未设置 keep-RGBs 时仍要把色调恢复到 100。

伪代码中 relative 测试在第 372–373 行，绝对写入位于该 `if` 内；第 523 行之后是相对加法分支。关键汇编排除了对反编译缩进或 goto 的误读：

```text
0x14003cdcb: AND R12D, 0x2
0x14003cdcf: JZ 0x14003d0ad
0x14003ceaa: ADD dword ptr [RDI + 0xac], EAX  ; target zoom width
0x14003cf97: ADD dword ptr [RDI + 0xb0], EAX  ; target zoom height
0x14003d095: ADD dword ptr [RDI + 0xb4], EAX  ; target transparency
```

RGB gate 则位于更早的 `0x14003c97e TEST R13B,0x4` / `0x14003c982 JNZ ...`，与 relative 无关。完整 [伪代码](consumer-contract-evidence/0x14003c6f0-pseudocode.txt) 和 [汇编](consumer-contract-evidence/0x14003c6f0-assembly.txt) 可复查。

当前 `src/game_pictures.cpp:370` 在 relative 分支只写 finish_x/y，跳过 `SetNonEffectParams`，而 keep-RGBs 处理又放在另一分支。这同时漏掉了两轴缩放、透明度和正常 RGB 更新。

### 3.2 duration=0 不等于零次状态更新

原版处理普通时长的步骤为：负值按帧数处理；非负普通值转换为六倍帧数并设置至少 1；keep-transition 使用既有剩余值，但小于 1 时也设为 1。这里讨论正常可表示范围，极值溢出应作为单独的整数位模式合同核对，不能随意增加夹限。

原版 `03c6f0` 伪代码第 141–161 行、汇编 `03c93e–03c96e` 包含这两处最小值处理。共享更新器 `06d8c0` 则只有在 remaining>0 时插值普通属性，remaining=0 时只减到 -1。两者应一起实现。

当前 `src/game_pictures.cpp:402` 对普通 duration=0 得到 time_left=0，keep-transition 也不修正既有 0/-1；`src/game_pictures.cpp:806` 随后不更新 current 属性。`ApplyOrigin(true)` 只调整 finish 坐标，绘制器仍读取 current 坐标，因而不能弥补这一连接缺口。

## 4. 游戏中各现象的消费链

### 4.1 白色尾迹：残影年龄没有进入缩放与透明度

`_workspace/script/cev/pinball/pbOnFrame.txt:50–59` 每帧把球位置写进循环使用的残影槽；`BA_MAX_AFTER=8`，起始图片编号 20。每张残影紧接着执行：

```text
.relative .pos(0,0) .scale(-80) .trans(100)
.keepRgbs .keepBlend .time(2)
```

实际公共事件 17 的动态图片移动，例如 command 350，参数为 `A5=-80, A6=100, A14=2, A15=22, A17=1`；A17 表示图片编号从变量取得。原版目标应是从基础 100 缩到 20、透明度从 0 增至 100，计划用 12 帧过渡；正常逐帧运行中槽在 8 帧后复用，较老残影在复用前已更小、更淡。

这里没有按欧氏距离直接计算透明度。游戏以时间间隔采样位置，残影年龄决定缩放和淡出；球速改变时空间间距随之改变。当前 relative 保留 100/0，使每个槽一直保持原尺寸和亮度，视觉上就失去了随尾迹延伸的变化。无需修改弹球物理轨迹或新增距离衰减算法。

### 4.2 得分结算提示：脚本结束显示状态，像素没有退场

地图 5、事件 2、page 1、command 81 的实际文本是：

```text
\c[0]得分结算
\c[5]\v[443]\c[7] x \v[444]\c[0] = \c[2]\v[453]
```

它进入 `DI_ST_LIQUID`，使用图片 151（背景）和 152（文字）。公共事件 17 中计时到 62 后，游戏会等 `anyInput==1`；这段等待是游戏设计，不能直接当成错误。

输入条件通过后，command 528/529 对两张图设置 `.relative .pos(0,4) .trans(100) .time(2)`，随后把 displayState 改为 NONE。**游戏没有立即 ErasePicture；它依赖最后这次淡出把图片变得不可见。** 当前代码只将位置下移 4，透明度目标仍为 0；状态机已结束管理，两张图便会继续留在页面上。

因此应区分：未输入时等待、输入后提示及背景仍可见、后续场景流程也不推进。这次静态证据直接解释第二种；如果后续流程也不推进，需要取得那个具体执行状态才能判断输入值或等待链，不能由画面残留推导输入系统坏了。

右侧 `PIC_LOG=143` 的加分历史则另有截行更新逻辑，本来没有同样的定时淡出。它不能与上述“得分结算”页面混为一谈。

### 4.3 右侧文字白色且偏大：过渡目标被保留了

公共事件 17 command 628/629 是 score 的创建与移动；bonus、multiplier、chance 使用同样模式：先创建 120% 缩放、RGB=200，再用 relative 的缩放 -20、RGB=100、time=1 恢复常态。

原版在 6 帧内从 120% 到 100%，并把 RGB 从 200 到 100。当前代码把两者都保留；`src/maniac_picture_renderer.cpp:198` 的高色调公式为 `c += (255-c)*(tone-100)/100`，tone=200 会将通道推到 255，正常转义色因而保持白色。截图里的白色和尺寸差异有这个上游原因，不能先归咎于字体、调色板或色调公式。

该原因修正之后，字体笔画、字形宽度和抗锯齿仍可能与原版不同；这是既定的 EasyRPG 字体边界，不应顺势扩成 GDI 字体移植。

### 4.4 底部操作说明缺失：无时长移动没有更新 current

地图 5、事件 6、page 1、command 31 创建图片 141，左上角为 (320,225)，开始在 320 像素画面外；command 49 在每帧递减横坐标后移动它。其实际参数 `A14=0`，不是“游戏根本没有创建文字”。

原版给每次 Move 至少一帧，在下一次图片更新中将 current 设为本次目标。当前 time_left=0 使 current 保持创建位置，因此背景进入了屏幕，文字仍在屏幕外。这条路径不依赖换字体或补字库。

### 4.5 其他静态可达的不可见文字

同一公共事件还有两种相反的入场方式：`DI_ST_ZOOM` 创建时 scale=0，再 relative scale=100；`DI_ST_CENTER` 创建时 trans=100，再 relative trans=-100。当前实现使前者一直零尺寸、后者一直完全透明。这说明“有些文字仍无法渲染”不仅是底部滚动说明一种表现。

本轮没有将所有缺字都归到这两个原因，也没有从不同时刻的两张截图估算几何偏差。黄字警告仍应按实际 warning 文本逐项对应；字体发现的 debug 信息和变量越界 debug 不能替代黄色 warning 的根因证据。

### 6.3 不再重演四个原因的有限交付方式

每个合同包先给出原版字段/分支表，再列出现有共享实现及实际消费者，最后记录已确认差异和缺证据处。入口只引用适用的合同，并核对该入口的参数转换和状态前提；不为每个 opcode 复制整套机制，也不把行数或断言总数当完成率。
