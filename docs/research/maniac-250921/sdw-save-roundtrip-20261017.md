# SDW：Player 存档回读 RPG_RT 时的 Common Event ID 0

2026-10-17，分析基线 `0382d28fc`。以下分析保留为修复前记录；随后经用户授权进行的修复、扩展检查与验证另列在文末。原始存档不改动。

## 结论

本次错误由 `SaveEventExecState/0x16/keyinput_variable` 的编码不兼容触发。游戏自带 Maniac 使用 BER 整数，Player/liblcf 仍使用普通旧版 RPG_RT 的原始单字节规则。公共事件 596 的按键输入目标变量为 2201，原档编码 `91 19`；Player 保存时将其截断为 153，再写成原始字节 `99`。

Maniac 的 BER 读取器将 `99` 的最高位视为续字节标志，继续读取后面的字段字节。读取位置由此错乱，最终公共事件记录的外层 ID 被读成 0。报错并非游戏真的调用了“公共事件 0”，也不是保存后丢失了整个公共事件数据库。

## 三份存档与二进制身份

|存档|来源/格式版本|公共事件 596 的状态字段 `0x16`|公共事件帧身份|
|---|---|---|---|
|Save03|原版，版本 0|`16 02 91 19`：长度 2，BER 2201|原有 20 个执行帧均有原版身份|
|Save04|旧 Player，版本 810|`16 01 99`：长度 1，原始 uint8 153|多出 11 个缺少原版身份的帧|
|Save05|Player3，版本 811|仍为 `16 01 99`|31 个公共事件执行帧的原版身份均已填写|

因此，Save05 证明上一轮 SF03 身份修复已经生效，但这处独立的编码错误尚未修复。目录中的 Player2 SHA-256 为 `d2076e3bb10368ede3d59a76f732f6f4e9e3d599d7aa7a0f36c64e5e55a381d9`，与此前检查的旧程序一致；Player3 为 `b75a53facc0d0e5e90a892d00c530f7273e03b9dc721f215cb5e60e35ec5db6f`。

游戏公共事件 596（名称 `★莉琉追加用(並列)`）的第 145 条命令，按 1 起算，是 `11610 KeyInputProc`，参数首项为 2201；后续条件分支也查询变量 2201。

## 实际错误进程的只读证据

用户保留 Save05 的错误窗口后，只读检查其 RPG_RT 进程（PID 14392）。游戏 RPG_RT SHA-256：`fff214a52aeb250e9dc0ff5f031d3c616320c0ed4b86106b32dba50a4b816816`。

错误线程的关键调用链，均为该二进制 RVA：

`0x7e9dd → 0x5af3f → 0x5aabd → 0xc5a57 → 0x201b9`

- `0x5ad20` 是公共事件存档表读取器；读取完后调用 `0x5a9f0` 重建并行公共事件列表。
- `0x5aa4a` 读取公共事件对象的 ID，减 1 后做无符号范围检查；ID 0 会在 `0x5aa53` 分支到错误路径。
- `0x5aab8` 调用错误函数 `0xc5a00`，格式为 `Invalid %s ID: %d`，名称参数为 `Common Event`。
- 实际内存中的列表仍有 1000 个对象，第 596 个对象 ID 为 596；**第 597 个开始出现错位，共 403 个对象 ID 为 0**。这与文件中本来正确的外层编号 1—1000 不同，说明错误发生在原版读取过程中。

原版对状态字段 `0x16` 的处理位于 `0x85125`：调用 BER 读取函数 `0xc6580`，随后把结果写入 32 位成员 `owner+0x18`；不是原始字节读取。

## 编码与消费路径

Player/liblcf 的定义在 `lib/liblcf/generator/csv/fields.csv:925`：

`SaveEventExecState,keyinput_variable,f,UInt8,0x16,0,0,0,`

生成成员是 `uint8_t keyinput_variable`。`src/game_interpreter.cpp:269` 的 `save.keyinput_variable = variable` 会将 2201 截断为 `2201 & 255 = 153`。liblcf 的 uint8 基础类型直接输出这个字节，不做 BER 编码。

源码第 200—202、267—269 行的注释明确说明这是为了模仿旧 RPG_RT 的 uint8 存档行为。对应代码来自上游历史提交 `4d18a403a`（2019-04-06）。问题在于当前 Maniac 保存/读取路径仍沿用该旧规则，没有针对实际 Maniac 格式分流。

EasyRPG 读取自己的 Save04/05 时仍按同一单字节格式解码，因此不会发生这里的 BER 续字节串位；这不表示变量编号未被截断。原版 Save03 的 2 字节字段在 EasyRPG 读取时也无法正确保留完整变量编号；本例的按键命令为不等待输入的轮询，后续执行会重新取得命令中的 2201，因此表面上仍能正常游玩，不能据此认为保存状态正确。

## 有限反证检查

在内存中按已核实的原版嵌套读取规则模拟流位置：

- Save03：1000 个公共事件 ID 全部正确，完整消费该字段。
- Save04、Save05：第 597 个记录首次变成 ID 0；Save05 产生 403 个 ID 0，与实际进程内存一致。
- 仅在内存中把 Save05 公共事件 596 的 `0x16` 恢复成 `91 19`，并重新计算外层长度后：1000 个 ID 全部正确，完整消费该字段。

这是静态规则的流位置模拟，不是修改后的存档已在 RPG_RT 实机通过。两个隐藏自动读档探针未达到加载消费点，没有纳入结论。实际运行证据来自用户已复现的错误进程只读采样；未对该进程执行状态修改或 UI 操作。

## 修复边界与另见问题

修复应在 Maniac 模式下保留完整变量编号，并按 BER 整数读写 `0x16`；普通 RPG_RT 仍需维持其既有字节规则。旧 Player 已截断的值无法仅靠该单字节完整恢复，不能给所有值机械补高位。

这项属于原有通用字段的 Maniac 格式差异，未带 `maniac_` 名称，未进入上一轮以 Maniac 命名字段及图片复用字段为主的 55 项清单。应扩展对原有字段的格式复用检查，而不是把上一轮结果当作完整存档兼容证明。

另见：地图 23 事件 128 的空并行帧在 Save04/05 中丢失原版类型、事件 ID 和页号，来源为 `src/game_event.cpp:106` 的空帧补写分支。它是独立的静态遗漏；本次实际报错位于公共事件列表重建，不据此将该空帧遗漏认作本报错的直接原因。

文件哈希、帧对比、调用栈摘要及原版机器码窗口见 [evidence.json](sdw-save-roundtrip-20261017/evidence.json)。游戏目录内的原始 Save03、Save04、Save05 和程序文件未改动；以上分析阶段未修改源码，后续授权处理如下。

## 授权后的修复与通用字段检查

修复将 `keyinput_variable` 的内存成员扩为 `int32_t`，使用字段适配器保留两种格式：单字节按旧字节值读取，多字节按 BER 读取；Maniac 写完整 BER 编号，普通 RPG_RT 写原始低字节。解释器的读档/保存也按当前模式选择完整编号或旧截断行为。选择格式的布尔值仅存在于运行时，不额外写入存档。

在扩展检查中，确认另外 9 个按键选择标志的原版格式是单字节，而通用定义为 BER 整数：`0x18..0x1C`、`0x23..0x26`。普通的 0、1、2、3 编码恰好相同；大于等于 128 的有效低字节会暴露差异。新增同组适配器，Maniac 写原始字节、普通格式保持既有 BER 规则；读取同时兼容原始单字节和旧 Player 的多字节表示。按键行为继续使用 EasyRPG 的输入抽象，未增加原生按键接口。

存档格式版本递增为 812。旧 Player 文件中的截断编号（例如 Save04/05 的 153）仍能读取，但不猜测已经丢失的高位；从原版 Save03 重新保存时可保留完整的 2201，以及前台状态中的 4085。

通用字段清单见 [general-field-audit.json](sdw-save-roundtrip-20261017/general-field-audit.json)：

- 共清点 319 项原版编号空间的通用字段定义，不再只按 `maniac_` 前缀筛选。
- 原始 Save03 实际覆盖其中 198 项定义、6917 处字段记录，递归检查标量长度、BER 完整性和定长数组元素宽度。已适配的五个图片复用字段单独识别，不用普通类型误报。
- 样本中发现两处 `keyinput_variable` 长度不符：前台 4085 和公共事件 596 的 2201；属于同一字段错误。
- 核对了 22 项执行状态通用字段的原版分支，以及 6 个 Int8 转场字段的原版写出代码。6 个转场字段仍是原始单字节，与现有定义一致。
- 除按键编号和上述 9 个标志外，本轮未发现其他未处理的编码差异。121 项未在样本中出现，字段语义、所有数值组合以及完整双向存档兼容均不据此宣称通过。原版不消费的 `0x1D/0x1E` 和只在合法值范围内编码相同的情形也不混算为新错误。

原版消费验证使用游戏自带 RPG_RT 的实际读取函数：在独立进程进入 WinMain 前构造内存流及 1000 个有效数据库 ID，调用原版公共事件表读取和 ID 校验，读取返回的编号及按键状态。数据库对象仅提供 ID 上界和非并行触发类型，不执行游戏事件。该探针不创建游戏窗口、不发送输入、不修改原始程序或存档；它验证原版读取器的具体消费路径，不代替完整游戏 UI 读档验收。每次独立进程均有期限并在结束后回收。

## 空并行帧身份修复（2026-10-17，独立后续）

`Game_Event::GetSaveData()` 为没有指令、没有执行栈的并行事件补写一个空帧。这条路径绕过 `Game_Interpreter::Push()`，原先只填写普通 `event_id`，导致 Maniac 身份字段默认归零。Save03 的地图 23／事件 128／第 3 页原本保存帧编号 1、类型 `0x14`、原版事件 ID 128、页号 3；Player 补帧时丢失这四项信息。这是保存元数据遗漏，仍不作为此前公共事件列表错位报错的直接原因。

修复限定在 Maniac 模式：补帧时写入编号 1、地图事件类型及并行触发方式、事件 ID、当前页号，以及 Player 的地图 SELF 身份。SELF 使用事件自身的地图 ID，避免误用玩家所在地图。非 Maniac 空帧保持原有字段；已有执行帧不改写。没有更改存档字段布局或版本号，也不增加事件指令。

验证结果见同目录 `sdw-save-roundtrip-20261017/empty-parallel-validation.json`。任务内临时消费者检查覆盖普通模式、Maniac 空帧、保存恢复、切换页号、非并行事件、已有非空执行栈，以及本次磁盘上 Save03／04／05 中事件 128 经 `SetSaveData → GetSaveData → LSD 保存／读取 → 再次 SetSaveData／GetSaveData` 的往返。检查读取实际地图的页条件与存档开关、变量，不改写游戏目录中的文件。临时测试源码在检查完成后移除。

修复前，两项临时用例有 84／163 条断言失败，均为缺失的身份字段；修复后 163／163 通过。相关既有检查实际执行 7 项、264 条断言通过，包括事件 ID、执行帧查询、并行续行、空调用帧、被调用地图身份和 SELF／返回目的地存档往返。另一个原版存档环境变量用例未配置输入而直接返回，不计入通过项。Windows Release Player 与测试程序构建通过。

此项验证不包含 RPG_RT 人工 UI 回读或完整游戏流程，也不包含 Android/Web 运行验收。
